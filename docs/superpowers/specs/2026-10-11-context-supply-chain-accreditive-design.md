# Context Supply Chain и сквозной сценарий «Аккредитив»

Дата: 2026-10-11  
Статус: утверждён пользователем

## 1. Цель

Встроить содержимое учебного прототипа `kontur_accreditive_context_demo.html` в КОНТУР как нативный, связанный с общей моделью данных маршрут работы со знаниями. Одновременно заменить демонстрационный сценарий «Копилка» на «Аккредитив» во всех разделах приложения и расширить существующий раздел «Документация» до полноценного справочника.

Пользователь должен пройти путь от классификации технической системы до сохранённого Context Bundle, а созданные по пути сущности должны быть видны в «Окружении», «Регуляторах», «Управлении знаниями», запусках и документации.

## 2. Границы работы

В scope входят:

- семь нативных интерактивных этапов Context Supply Chain внутри «Управления знаниями»;
- общая серверная модель для систем, сегментов, политик, онтологии, знаний и Context Bundle;
- сквозной seed «Аккредитив» для основного демонстрационного сценария;
- интеграция опубликованных данных с существующими разделами приложения;
- расширение автономной HTML-документации и перенос туда промышленной архитектуры;
- автоматические проверки доменной логики, действий engine/API, рендера и сборки.

В scope не входят:

- настоящий Neo4j, vector database или внешний Context Service;
- загрузка нормативных документов из внешних систем;
- юридическая интерпретация правил конкретного банка;
- замена существующего универсального сценария создания продукта «с нуля»;
- отдельная дизайн-система для учебного маршрута.

## 3. Основные решения

### 3.1. Нативная интеграция

Маршрут реализуется React-компонентами в текущем shell приложения. Исходный HTML не подключается через iframe и не сохраняет данные в `localStorage`. Все изменения проходят через общий state, engine и существующий API.

### 3.2. Единый источник истины

Существующие сущности используются там, где они уже выражают нужную модель:

- `Team.bindings` описывают репозитории, технические системы и их сегменты;
- `State.policies` хранит версии Policy Package, требования, применимость и evidence;
- `State.knowledge` хранит Product и Team Knowledge и их жизненный цикл;
- `Product`, `Team`, `Task`, `Capability`, `Run` и их snapshot продолжают задавать рабочий scope.

К state добавляются только отсутствующие понятия:

- категории онтологии продукта;
- понятия аккредитива и ссылки на источники;
- сохранённые неизменяемые Context Bundle.

Граф знаний является вычисляемым представлением общих сущностей. Отдельной копии графа в state нет.

### 3.3. Детерминированная поставка контекста

Context Bundle собирается по четырём независимым путям отбора:

1. `Product + productTopic` выбирает опубликованные Product Knowledge и понятия онтологии.
2. `Team` выбирает опубликованные Team Knowledge.
3. `System → Segment + workType` выбирает обязательные опубликованные Policy Package.
4. `stage` определяет объём инструкций и evidence для Before Plan, Implementation или Verification.

Каждый включённый фрагмент содержит источник, версию и объяснение причины отбора. Обязательства не выбираются similarity search.

## 4. Доменная модель

### 4.1. Категория понятия

Категория группирует понятия продукта: основы, сценарии клиентов, виды сделок, реквизиты, способы платежа, комиссии и участники.

Минимальные поля:

- `id`;
- `productId`;
- `title`;
- `description`;
- `order`.

### 4.2. Понятие продукта

Понятие — типизированный узел Product Knowledge Graph.

Минимальные поля:

- `id`;
- `productId`;
- `categoryId`;
- `label`;
- `description`;
- `variant`: `all`, `individual` или `corporate`;
- `sourceRefs`;
- `status` и `version`.

### 4.3. Расширение Knowledge

Knowledge сохраняет текущий жизненный цикл `proposed → approved/rejected` и дополняется необязательными полями:

- `conceptIds`;
- `sourceRefs`;
- `summary`;
- `publishedAt`.

Старые записи без этих полей остаются читаемыми.

### 4.4. Context Bundle

Сохранённый bundle содержит:

- стабильный `id` и детерминированный `hash` содержимого;
- `productId`, `teamId`, `systemId`/binding и вычисленный segment;
- `productTopic`, `workType`, `stage`;
- выбранные понятия, Product Knowledge, Team Knowledge и Policy Package;
- `selectionReasons` для каждого элемента;
- `sourceVersions`;
- `unknown` и блокирующие причины;
- `createdAt`, `createdBy`;
- готовый текстовый фрагмент для агента;
- статус Delivery Receipt.

После сохранения bundle не редактируется. Новая сборка создаёт новый snapshot.

## 5. Действия и поток данных

Существующие actions повторно используются для систем, политик и знаний. Они расширяются метаданными только там, где это необходимо.

Новые операции:

- компиляция preview Context Bundle без изменения state;
- сохранение валидного bundle как immutable snapshot;
- при необходимости получение bundle по ID для запуска и просмотра.

Компилятор оформляется как чистая доменная функция. Engine/API отвечает за RBAC, проверку актуальности входных данных и сохранение snapshot. Hash вычисляется из канонического payload без времени создания и случайного ID.

Запуск может ссылаться на сохранённый bundle. Ссылка не меняет уже замороженные версии в существующем Capability/Run snapshot.

## 6. Интерфейс «Управление знаниями»

### 6.1. Пользователь и характер интерфейса

Основные пользователи — Product Engineer, Platform Engineer, Product Owner и Regulator, которые последовательно классифицируют систему, публикуют контролируемое знание и проверяют состав контекста перед автоматизированной работой.

Интерфейс должен ощущаться как технический, спокойный и пригодный для аудита. Он сохраняет текущую типографику, spacing и borders-only глубину КОНТУРа.

### 6.2. Доменная визуальная система

Ключевые понятия: источник, цепочка, сегмент, политика, понятие, evidence, snapshot, квитанция доставки.

Цветовые роли:

- Product Knowledge — существующий зелёный;
- Regulatory Policy — приглушённый фиолетовый;
- Team Knowledge — шалфейный;
- системы и сегменты — стальной синий;
- незакрытые вопросы и предупреждения — янтарный.

Цвет используется только для семантики. Новые случайные hex-цвета и отдельная тёмная тема исходного HTML не переносятся.

### 6.3. Визуальная подпись

Подпись раздела — три трассируемые линии Product, Policy и Team, сходящиеся в карточку-квитанцию Context Bundle. Этот мотив повторяется в обзоре, объяснении отбора, графе и результатах сборки.

Стандартные решения, которых нужно избежать:

- отдельный второй app shell заменяется контекстной шкалой этапов;
- безликие metric cards заменяются карточками источников с версиями и provenance;
- обычная таблица результатов заменяется трассировкой отбора и Delivery Receipt.

### 6.4. Навигация

Внутри текущего раздела появляется компактная шкала из семи этапов. На широком экране она располагается слева от рабочей области. На узком экране превращается в горизонтальный прокручиваемый переключатель. Текущий этап кодируется в route/tab, поэтому его можно открыть напрямую и восстановить после reload.

### 6.5. Семь этапов

1. **Обзор.** Три источника контекста, схема их слияния, статус данных и начало маршрута.
2. **Сегментация систем.** Выбор LC Retail Service или Trade Finance LC, редактирование сегмента и путь `Repository → System → Segment`.
3. **Policy Package.** Создание, review и публикация требования с применимостью по segment/work type и правилами evidence.
4. **Онтология аккредитива.** Категории и понятия retail/corporate, сделки, реквизиты, платежи, комиссии и участники.
5. **Публикация знаний.** Proposal, привязка к понятиям и источникам, review, публикация в Product или Team Knowledge, существующая витрина знаний.
6. **Граф знаний.** Фильтры, интерактивный SVG, инспектор узла и учебные Cypher-запросы, вычисляемые из общего state.
7. **Доставка агенту.** Форма scope, причины отбора, preview bundle, сохранение snapshot, история, копирование и скачивание JSON.

Каждый этап содержит прямую ссылку на соответствующую главу документации.

## 7. Документация

Существующая автономная страница `public/docs/kontur-architecture.html` остаётся точкой входа. Её копия в `dist/docs` обновляется сборкой, а не редактируется как отдельный источник истины.

Структура документации:

1. обзор платформы, роли и путь от задачи до доверенного запуска;
2. Context Supply Chain: Authoring → Control Plane → Graph/Search → Runtime;
3. сквозной пример «Аккредитив» для retail и corporate;
4. регуляторы, Policy Package, версии и отзыв;
5. Flow и доставка контекста на разных стадиях;
6. Sandbox, окружение и bindings;
7. Knowledge Graph, онтология, публикация и поиск;
8. контекстный ассистент и границы полномочий;
9. Trusted Capability, UAT, риск и production;
10. API Context Service, JSON-примеры и минимальная Cypher-схема;
11. гарантии эксплуатации: ACL, deterministic obligations, immutable snapshots, revoked policy и audit trail;
12. глоссарий и источники.

Промышленная архитектура из восьмого экрана исходного HTML переносится в главы Context Supply Chain, API и гарантии. Все примеры «Копилки» в документации заменяются на «Аккредитив».

## 8. Демонстрационные данные «Аккредитив»

Основной seed содержит один продукт «Аккредитив» и две команды:

- LC Retail Engineering;
- Trade Finance Engineering.

Минимальный технический контур:

- LC Retail Service и репозитории retail-сценария в сегменте `retail.backend`;
- Trade Finance LC и репозитории корпоративного сценария в сегменте `corporate.backend`.

Задачи, доски, Flow, Capability, Policy Package, Knowledge, запуски, уведомления, сообщения, suites и benchmarks получают согласованные аккредитивные названия и scope. Идентификаторы, на которые опираются внутренние связи, меняются только вместе со всеми ссылками и тестами.

Seed должен демонстрировать различие между продуктовым вариантом клиента и техническим IT-сегментом: `individual/corporate` у понятия не подменяет `retail.backend/corporate.backend` у системы и политики.

Пустой сценарий остаётся доменно нейтральным.

## 9. Роли и права

- Platform Engineer классифицирует систему и bindings.
- Regulator создаёт и публикует Policy Package.
- Product Engineer предлагает знания и собирает Context Bundle.
- Пользователь с `knowledge.review` рассматривает и публикует Knowledge Proposal.

Все этапы доступны для чтения любой роли в текущем product/team scope. Недоступное действие остаётся видимым, но disabled, с пояснением требуемой роли или permission и возможностью воспользоваться существующим переключателем демонстрационной роли.

## 10. Ошибки и пограничные состояния

- Система без сегмента попадает в `unknown`; Policy selection не выполняется.
- Отсутствующее опубликованное Product Knowledge показывается как незакрытый вопрос.
- Отсутствие Team Knowledge допустимо и явно отмечается в составе.
- Неоднозначный product alias или неизвестная тема не выбираются молча.
- Draft и rejected Knowledge/Policy не доставляются агенту.
- Retired/revoked policy блокирует сохранение нового bundle для затронутого scope.
- Deprecating policy включается с предупреждением и датой sunset.
- Повторная публикация уже рассмотренного proposal отклоняется.
- Изменение источников после preview требует повторной компиляции перед сохранением.
- Пустые состояния каждого этапа объясняют следующий допустимый шаг.
- Учебный граф и Cypher явно маркируются как эмуляция без подключения к Neo4j.

## 11. Проверки

### 11.1. Доменные unit-тесты

- отбор Product/Team/Policy по scope;
- различия retail и corporate;
- фильтрация по теме, work type и stage;
- исключение draft/rejected сущностей;
- поведение deprecating и retired policy;
- стабильность hash для одинакового канонического payload;
- новый hash при изменении версии источника;
- неизменяемость сохранённого bundle;
- сохранение поддержки старых Knowledge без новых метаданных.

### 11.2. Engine/API-тесты

- RBAC для сегментации, policy, knowledge и bundle;
- optimistic/stale preview validation;
- сохранение и чтение Context Bundle;
- persistence после reload;
- существующий жизненный цикл Knowledge и Policy.

### 11.3. Render-тесты

- рендер всех семи этапов с наполненным и пустым state;
- disabled/read-only состояния для разных ролей;
- навигация между этапами и переходы в документацию;
- витрина опубликованных знаний, граф, bundle preview и история;
- новые аккредитивные данные в основных разделах приложения;
- отсутствие пользовательских названий «Копилка» в демо-сценарии и документации.

### 11.4. Общая верификация

- полный `npm test`;
- `npm run typecheck`;
- production build;
- проверка собранного `dist`;
- визуальная проверка маршрута и документации на desktop и mobile.

## 12. Критерии приёмки

Работа считается завершённой, если:

1. пользователь может пройти семь этапов от системы до сохранённого Context Bundle;
2. сегмент, Policy Package и опубликованное Knowledge видны в соответствующих существующих разделах;
3. bundle объясняет выбор каждого источника и хранит версии;
4. повторная сборка с тем же содержимым даёт тот же content hash, а сохранённый snapshot не изменяется;
5. retail и corporate дают различимый policy/team контекст при общем Product Knowledge;
6. основной демонстрационный сценарий во всех разделах посвящён аккредитиву;
7. документация содержит утверждённые главы, сквозные ссылки и промышленную архитектуру;
8. весь существующий test suite, typecheck и build проходят без ошибок.
