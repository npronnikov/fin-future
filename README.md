# КОНТУР — React + Node.js · 1.5.0

Самостоятельное локальное приложение на React + Vite и Node.js с SQLite. В архив включены исходники и готовая сборка интерфейса. Светлое оформление, схема Flow и инспекторы основаны на Autonomous Studio из вложения.

## Быстрый запуск

1. Установите **Node.js 24** с npm.
2. Полностью распакуйте архив и откройте терминал в папке `kontur-react-node`.
3. Выполните:

```sh
npm start
```

4. Откройте **http://127.0.0.1:3000**.

Готовый `dist/` уже включён. Для обычного запуска установка npm-зависимостей и повторная сборка не нужны; SQLite входит в Node.js. После установки Node.js приложение запускается без доступа к интернету. Команды одинаковы для Windows, macOS и Linux.

Остановка — `Ctrl+C`. Повторный `npm start` продолжает работу с сохранёнными данными.

| Принятие риска | Отдельная форма с рисками, галочкой ознакомления, комментарием и автором решения. Явно указаны отсутствие корзины и большой риск при менее чем 100 завершённых прогонах. |

## Сценарий с демонстрационными данными

Выберите **«Открыть с данными»**. Доступны продукт «Аккредитив», команды Trade Finance Engineering и LC Retail Engineering, две доски задач, настроенная среда, Flow, Context Supply Chain и история исполнения. Вверху можно переключить демонстрационную роль.

### Уведомления

Нажмите **колокольчик**: в нём показаны последние события выбранной команды. Выбор события отмечает его прочитанным и открывает **реестр уведомлений**. Прямой переход в реестр находится внизу списка.

В реестре можно отфильтровать события по типу и прочтению, найти их по тексту, открыть подробности, перейти к связанному запуску / Capability / Environment и отметить все уведомления текущей команды прочитанными. Человеческие решения по Gates доступны в Automation → Human Gates и в запуске. Каждый новый гейт, в том числе при следующей попытке, создаёт уведомление.

### Эмуляция продакшна

1. Откройте **Capabilities → Dependency Update** в роли Product Engineer команды-владельца.
2. Нажмите **«Эмулировать продакшн»**, затем **«Запустить эмуляцию продакшна»**.
3. Приложение последовательно обработает подходящие незавершённые задачи с тегом capability во всём продукте, включая разные доски и команды.
4. Дождитесь анимированного прогона стадий Flow. Посмотрите выполненные задачи, причины пропуска и доступные ссылки на запуски. Завершённые задачи перейдут в колонку **«Готово»**.

Эмуляция использует **точный released snapshot**. Ни Human Input, ни Approval, ни согласование Specification не приостанавливают этот прогон. Узлы человеческого согласования отражаются как автоматически пропущенные в режиме выпущенного Flow; человеческие решения и показатели ручного участия не создаются. Regulatory Plan, автоматические проверки и Evidence сохраняются.

Задачи, которые уже завершены, имеют активный запуск или не соответствуют текущим ресурсам и разрешениям, пропускаются с объяснением. Повторная эмуляция не запускает уже завершённые задачи повторно. Отозванная или приостановленная capability не запускается. При допустимом `migration_required` действует существующая политика релиза до окончания grace period.

### Messenger и ассистент

В Messenger доступны общий канал команды и обсуждения её запусков. Сообщения можно искать; вкладка «Упоминания» собирает сообщения с `@имя` / `@id` пользователя. Enter отправляет сообщение, Shift + Enter добавляет строку. В обсуждении задачи есть переход к запуску. Гейтов в Messenger нет.

Чат ассистента открывается круглой кнопкой справа снизу. Он остаётся доступным при переходах между разделами и использует контекст текущего экрана; в HG SDLC запуск получает snapshot, гейт и артефакты этого запуска. Ответы демонстрационные. Сообщение ассистенту не принимает гейт, не меняет ресурсы и не выпускает capability.

### Supervised, Rework и Takeover

- **RUN-912 в Automation → Human Gates:** Human Input по зависимости и дальнейшее Approval.
- **RUN-913:** Specification перед Implementation.
- **Request Rework:** укажите комментарий. В том же запуске начинается следующая попытка с первого узла; в SDD заново проходит и согласование Specification. На узлах отображается номер попытки. В Attempts доступны прежние артефакты, решения и прохождение узлов.
- **Takeover:** нажмите кнопку у гейта, оставьте комментарий и подтвердите передачу управления. Система сообщает: «Идите в IDE и редактируйте проект там, а потом верните управление». По возвращении заполните «Комментарии» и нажмите «Вернуть управление». Обе записи сохраняются с автором и временем. Проверки после возврата выполняет эмуляция Flow.

### UAT и принятие риска

Путь выпуска: **История запусков → frozen snapshot → UAT → принятие риска → Production**.

Нажмите **«Эмулировать UAT»** на Release Snapshot. Система выполнит демонстрационный прогон тестов и корзин, включённых в этот snapshot; человеческие гейты не запрашиваются. Версии корзин и тестовые cases фиксируются при создании нового snapshot. Более позднее редактирование корзины не меняет уже замороженный выпуск. Статус обычной задачи, использованной для UAT, не изменяется.

После успешного UAT откройте **«Ознакомиться с рисками»**. Форма показывает фактическую оценку этого snapshot: «Нет тестовой корзины», если корзина отсутствует; «Большой риск из-за малой статистики», если завершённых прогонов меньше 100; проблемы приложенной корзины, если они есть. Также указано, что выпущенный Flow будет работать без гейтов. Участник с `risk.accept` отмечает галочку ознакомления, оставляет комментарий и фиксирует принятие риска либо отклоняет его. Только после принятия доступен выпуск в Production.

Стадия Admitted в интерфейсе обозначает принятие риска. **Benchmark Lab** остаётся отдельной необязательной оценкой Test Suite по тегу.

### Отчёт по задачам

На **Capabilities** нажмите **«Отчёт по задачам»** у нужной capability. Откроется `#/capability/<id>/history`; этот же отчёт доступен из вкладки capability.

Отчёт показывает уникальные задачи, для которых были запуски выбранных версий Flow, и доли задач с Rework, Takeover и только Approval. UAT исключён. Если у задачи были и Rework, и Takeover, она учитывается в обеих группах; поэтому эти два процента могут пересекаться. «Только Approval» означает, что все её выбранные запуски приняты с Approval без Human Input, Rework и Takeover. Знаменатель указан прямо в отчёте. Ниже остаются статистика и список запусков; видны только задачи выбранной команды.

## Сценарий с нуля

Выберите **«Открыть настройку с нуля»**. Доступны демонстрационные профили, общий Catalog и Regulatory Context. Продуктов, команд, досок, задач и истории ещё нет.

### 1. Продукт и команда

В роли **Product Owner** создайте Product: название, описание и при необходимости цели. Затем создайте Team и укажите область ответственности. Team Space появляется сразу.

На Home откройте следующий шаг **People**. Добавьте в команду Platform Engineer и Product Engineer. В Permissions выберите нужные разрешения; для рассмотрения supervised-результатов требуется **Проверка capability (capability.review)**. В списке показываются русские названия с английскими кодами.

### 2. Environment — мастер Platform Engineer

На Home нажмите **«Подключить ресурсы»**. Переход выполняется в роли Platform Engineer команды.

**Resources**

Подключите три ресурса кнопкой **«Подключить ресурсы» / «Подключить ресурс»**:

- **Git-репозиторий:** выберите репозиторий из каталога. Настройте чтение, запись, администрирование и создание pull request. Для выполнения изменяющих код задач нужна запись.
- **Task Tracker:** выберите проект в scope. Доступны демонстрационные проекты `KOPILKA`, `GROWTH`, `PAYMENTS`.
- **Jenkins CI:** выберите pipeline в scope, например `kopilka/build-and-test`.

Каждый ресурс сохраняется кнопкой **«Сохранить биндинг»** и появляется в списке. После подключения обязательных ресурсов нажмите **«Далее · Workflow Platform»**.

**Workflow Platform**

Выберите одну из платформ:

- **HG SDLC — Externally orchestrated**.
- **AI Manager — Agent directed**.

Нажмите **«Далее · Finish»**: выбор сохраняется.

**Finish**

Настройте параметры Sandbox. Схема показывает платформу, компоненты, границу Sandbox и подключённые ресурсы; элементы схемы можно выбрать для просмотра сведений.

Рядом находятся кнопки **«Сохранить конфигурацию»**, **Preview** и **Provisioning**. Откройте Preview и проверьте актуальную схему. Provisioning доступен в этом окне и на основном экране после просмотра. Если конфигурация изменилась, перед Provisioning снова показывается её Preview.

После успешного Provisioning нажмите **«OK · На Home»**. На Home среда отмечается созданной, следующим шагом становится создание доски и задач. Кнопка создания доски переключает на подходящего участника команды с ролью Product Engineer или Product Owner.

### 3. Доска и задачи

Создайте **новую доску** — название и описание. Можно создать несколько досок одной команды. Добавьте моковые задачи: выберите доску, набор, количество от 1 до 12 и исполнителя.

Kanban содержит пять колонок: Backlog, К работе, В работе, На проверке, Готово. Есть фильтры по доске, assignee и тегу. Моковые задачи добавляются только кнопкой справа сверху. Карточки можно перетаскивать или редактировать через детали задачи. Активный запуск управляет статусом и фиксирует тег задачи до завершения.

### 4. Выбор Flow из каталога

Нажмите **«Выбрать Flow» / «Добавить Flow»** на доске. Откроется вкладка **Flow** в Catalog.

1. Откройте карточку нужного Flow: Dependency Update, Statements & Certificates или Custom Flow.
2. Посмотрите описание и предварительную схему с Regulatory Plan / Evidence.
3. Нажмите **«Выбрать Flow»**.
4. Выберите тег задач, задайте название и нажмите **«Создать и настроить»**.
5. Откроется `#/capability/<id>/configuration` созданной рабочей конфигурации.

Если Flow для этого продукта и тега уже есть, каталог предлагает открыть существующий общий Flow. Ещё одну независимую сущность для той же пары создавать не требуется.

### 5. Настройка и ручной запуск

На схеме выберите узел. Справа находятся:

- **Настроить:** общее название и описание Flow, название узла, исполнитель, вход, результат и лимит доработок; для Checks — среда проверки. Исполнитель — кодинг-агент или человек; для человека выбирается Input gate либо Approval gate.
- **Skills:** инструкции шага и подключённые точные версии skills.
- **Subagents:** подключённые версии помощников из каталога. Сам каталог содержит отдельную вкладку Subagents с описаниями.

Узлы можно добавлять, переставлять и удалять, в том числе отдельный Input gate со свободным ответом на настроенный вопрос. Системные стадии До запуска / Regulatory Plan и После запуска / Regulatory Evidence остаются частью исполнения.

Под схемой раскройте **«Общие настройки Flow»**. Здесь находятся **Context Supply Chain** и **Экономика**. В экономике выберите GLM, GPT или Claude Sonnet, задайте лимит токенов на задачу и посмотрите приблизительную стоимость в рублях. Расчёт использует условные демонстрационные тарифы и не является фактическим прайсом поставщиков.

Нажмите **«Сохранить Flow»** либо **«Сохранить шаг»** — сохраняются все текущие изменения рабочей конфигурации в командном пространстве. При изменении содержания или названия версия автоматически повышается, например `v1.0 → v1.1 → v1.2`. Без новых изменений повторного повышения нет. Каталожный шаблон и старые снимки запусков не меняются. Затем **«Запустить задачу»**, выберите доску и задачу. Ручной режим — **Supervised**. Кнопка **«Сохранить и запустить Flow»** сначала сохранит оставшиеся изменения.

Откроется запуск с Timeline, прохождением узлов, Input / Approval, Rework, Takeover и артефактами. Rework повторяет весь Flow с первого узла; прежние попытки остаются в Attempts. После выпуска capability автоматические прогоны выполняются кнопкой «Эмулировать продакшн».

## Сборка Policy Packages

В роли **Regulator** откройте Regulation, выберите сегмент и направление, затем создайте пакет или новую версию существующего.

1. Во вкладке правил добавьте карточки и напишите текст каждой политики. Одно правило может содержать несколько строк.
2. При необходимости задайте применимость: тег задачи и тип работы, а также ожидаемые подтверждающие артефакты и verification Skill. Существующие условия пакета сохраняются при открытии новой версии.
3. Во вкладке **Skills** выберите нужные элементы из каталога; поиск помогает найти их по названию и ID.
4. Во вкладке **Subagents** выберите помощников. Пакет хранит точные версии выбранных элементов.
5. Укажите изменения и сохраните пакет. Для изменённого текстового правила повышается версия самого правила, ссылки применимости и Evidence переназначаются на неё.

Состав пакета показан карточками: текстовые правила, Skills и Subagents. Ни в редакторе, ни в обычном просмотре не требуется вводить массивы JSON. Прежние версии Policy Packages, snapshots и закреплённые зависимости остаются неизменными; публикация и Impact analysis работают как раньше.

## Общий Flow продукта и видимость команд

Доска принадлежит продукту и команде, задача — конкретной доске. Все доски продукта используют Flow по общей паре **продукт + тег**. Команда-владелец настраивает и выпускает Flow; другая команда того же продукта может открыть его и запустить свои задачи при подходящей среде и подключённых ресурсах.

Доски, задачи, запуски, сообщения и уведомления выдаются API с учётом членства пользователя в командах. Переключатель контекста показывает доступные команды. В выбранном Team Space видны только его задачи и статистика. Общая эмуляция может обработать задачи других команд продукта, но в её ответе скрыты чужие карточки и ссылки; остаются общие числа выполнения.

Для supervised-запуска общего Flow решение принимает участник команды задачи с `capability.review`. Released snapshot не переписывается ради назначения reviewer или изменения рабочего контекста.

## Очистка и переключение сценариев

Верхняя кнопка **«С данными» / «С нуля»** возвращает к выбору. У сценариев отдельные данные и ревизии, результаты каждого сохраняются.

В сценарии с нуля кнопка **«Очистить данные»** открывает подтверждение. **«Очистить и начать заново»** удаляет созданные продукты, команды, доски, задачи и историю только этого сценария и возвращает к созданию продукта. Демоданные другого сценария сохраняются. Устаревшие вкладки не могут записать изменения поверх очистки.

## Обновление предыдущей версии

1. Остановите сервер.
2. Распакуйте новую версию в отдельную папку.
3. Перенесите туда **`data/`** и при необходимости **`.env`**.
4. Выполните `npm start` и обновите страницу.

Ранее созданные проекты становятся досками с прежними ID и задачами. Сохраняются адреса существующих Flow, данные обоих сценариев, настройки узлов, артефакты и история. Каталог содержит Flow и Subagents; редактируемые старые узлы используют двух исполнителей. Старые frozen snapshots не нормализуются. Если в старых данных были несколько Flow с одинаковыми продуктом и тегом, они сохраняются для истории; для нового выбора используется основной Flow.

Миграция не меняет исторические frozen snapshots. Просмотр старой конфигурации не записывает новые поля автоматически. Сохранившийся в предыдущей версии незавершённый UAT на человеческом гейте автоматически продолжается без новых гейтов; его snapshot и прежняя история сохраняются. Сохранение существующего Git-биндинга с теми же Permissions сохраняет его прежние grants. Семантическая смена ресурсов требует нового Provisioning.

## Данные, настройки и разработка

SQLite хранится в **`data/kontur.sqlite`**. Каталог и таблицы создаются автоматически. Пересборка интерфейса не очищает данные. Для резервной копии остановите сервер и скопируйте папку `data/`.

Необязательные настройки задаются в `.env`, созданном из `.env.example`:

```dotenv
HOST=127.0.0.1
PORT=3000
DATA_FILE=./data/kontur.sqlite
```

Для изменения исходников:

```sh
npm ci
npm run dev
```

Откройте **http://127.0.0.1:3000**. React обновляется через Vite HMR. Серверный watcher следит только за собственными исходниками `server/` и `lib/`; `.vite-temp`, `node_modules/`, `dist/` и `data/` не вызывают циклических перезапусков.

После изменений:

```sh
npm run build
npm test
npm start
```

Перед переключением между `dev` и `start` остановите предыдущий процесс через `Ctrl+C`. Изменения `.env` требуют перезапуска.

| `components/kontur/tasks.tsx` | Доски, задачи, фильтры и Kanban |

| `components/kontur/configuration.tsx`, `flow-editor.tsx`, `flow-launch.tsx` | Редактор, экономика и supervised-запуск |
| `components/kontur/capabilities.tsx` | История, релизы, эмуляция и мониторинг |

Node.js исполняет `.mjs` и общие `.ts`-модули; JSX компилирует Vite. Для SQLite используется встроенный `node:sqlite`.

**Внешние интеграции демонстрационные.** Git, Task Tracker, Jenkins, HG SDLC, AI Manager и модели не подключаются к реальным корпоративным системам. Provisioning, задачи, исполнения, subagents, проверки и Judge моделируются локально. В приложении используется демонстрационный выбор ролей, корпоративная аутентификация не реализована.

## Если приложение не запускается

- **Нет `node` / `npm`:** установите Node.js 24 и заново откройте терминал; проверьте `node --version`.
- **Порт занят (`EADDRINUSE`):** остановите предыдущий процесс или измените `PORT` в `.env`.
- **Нет `dist/`:** полностью распакуйте архив или выполните `npm ci` и `npm run build`.
- **Старый интерфейс:** остановите сервер, выполните `npm run build`, снова `npm start` и обновите страницу.

Автоматические проверки используют отдельные временные базы и копии приложения. Пользовательский `data/kontur.sqlite` не изменяется.
