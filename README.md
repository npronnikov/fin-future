# КОНТУР · Team Space 6

**Запускаемая локальная mock-реализация по приложенной спецификации 6.0.**
Один React-интерфейс, один Node.js-сервер, сохраняемая предметная модель. Внешние ресурсы, агенты, LLM, Git/CI и rollout эмулируются. Настоящие сервисы и токены не нужны.

Это рабочая сборка `6.0.0-prototype.1`, **не заявление о закрытии всех 100 критериев**. Результаты отдельных тестов, ограничения и статус каждого критерия находятся в `reports/`. Исходный план приёмки сохранён без изменений в `docs/acceptance-plan.json`.

## Запуск готовой сборки

Проверенная среда: **Node.js 22.16.0, npm 10.9.2, Linux x86_64**. Версия также указана в `.nvmrc`. Другие версии/ОС не объявляются проверенными.

Распакуйте архив, откройте терминал в каталоге `kontur-teamspace` и выполните:

```sh
npm start
```

Откройте `http://127.0.0.1:4310`. Установка npm-пакетов, доступ к интернету и сборка перед первым запуском **не нужны**. Файл `dist/web/index.html` нельзя использовать вместо сервера: решения и состояние живут в backend.

Сервер по умолчанию слушает только loopback. Остановка — `Ctrl+C`. Повторный `npm start` восстанавливает сохранённую работу. Не публикуйте этот демонстрационный сервер в интернете: выбор demo identity намеренно не требует пароля.

Дополнительные параметры (пример для POSIX shell):

```sh
PORT=4311 DATA_DIR=/absolute/path/kontur-data npm start
```

В PowerShell: `$env:PORT="4311"; $env:DATA_DIR="C:\kontur-data"; npm start`.

## Сохранение и восстановление

По умолчанию данные появляются в `data/` рядом с `package.json`: `state.json`, проверяемый `state.backup.json` и блокировка единственного писателя. В архиве пользовательской data-directory нет. Не запускайте два экземпляра с одним `DATA_DIR`. Не удаляйте данные при работающем сервере.

При повреждении основного snapshot сервер открывает **read-only recovery mode** из проверенного backup. Максим может подтвердить восстановление; повреждённый файл сохраняется отдельно. Если проверенного backup нет, сервер завершает запуск с ошибкой — тихого сброса в пустое состояние нет. Экспорт пространства доступен в интерфейсе; проверка и применение импорта — через API, только в новую область ID.

## Первый сквозной маршрут

Первый экран пуст. Кнопка «Подготовленный пример» — отдельный явно обозначенный fixture, она не выдаёт историю за действия пользователя и не создаёт готовых релизов.

1. **Максим, платформенный инженер.** Создайте пространство. В setup выберите шаблон и сеть; рассчитайте план, подтвердите заказ, дождитесь аттестации. Отдельным действием установите `HG SDLC`. Все восемь каталоговых профилей являются mock adapters; Frontier обозначен только как mock-connection.
2. **Анна, владелец продукта.** Создайте проект «Статусы заявок». **Максим:** в «Интеграции и доступы» создайте repo, CI и model bindings.
3. **Иван, продукт-инженер.** Создайте Flow в Studio, проверьте граф и нажмите «Пробный запуск». Trial работает в Sandbox без CapabilityRelease. Сценарий «503 ≠ пустая выдача» специально даёт ошибочную первую реализацию.
4. В рабочем треде ответьте на Input Gate. Обычное сообщение и emoji не закрывают гейт. В Workbench изучите изменения и независимые checks. Верните неверный результат с причиной «503 не означает пустую выдачу» и ожидаемым исправлением. Первая попытка и её артефакты останутся в истории.
5. Сохраните предложение знания. **Мария, второй продукт-инженер:** опубликуйте его после проверки. **Иван:** явно подключите опубликованную версию в Studio и сохраните новый draft. Старый Run не обновит pinned зависимости. Новый Trial со сценарием «Применение знания» использует новый snapshot.
6. После принятого Trial выполните evaluation и создайте кандидат. **Мария:** independent technical review. **Анна:** решение об области и риске. **Максим:** подготовка UAT-среды. **Иван:** UAT и принятие его отчёта. **Анна:** допуск. **Максим:** явное размещение. Новые Released Runs используют snapshot Deployment, а не текущий draft.

Оставшийся после Rework Run можно принять отдельно через Human Inbox. Для ProductRelease используйте отдельную вкладку «Product Release»: технический пакет → PO → размещение → синтетический outcome → подтверждённая новая задача. PlatformRelease в этой сборке — **только отдельный draft-пакет**, не законченный процесс допуска платформы.

## Другие рабочие модули

Studio хранит граф, редактируемые узлы и переходы, JSON preview/import/export, Actor и Assistant Team. Для команды классы `ui` и `docs` дают разные планы специалистов; child tasks/runs связаны с проектом и одним root budget. Trial допускает оба класса команды, **Released-допуск этой сборки ограничен одним проверенным классом snapshot**. Другой класс требует отдельной конфигурации и UAT.

В интерфейсе доступны каналы/треды/mentions, Human Inbox, личный ассистент с подтверждением действий, доска задач, Markdown-знания/иерархия/типизированные backlinks, версии компонентов, арена, расходы, аудит, среды и incidents. Доступность кнопки не заменяет серверную проверку права. Неподдерживаемый adapter control возвращает ошибку.

Есть pause/step/cancel, InDoubt reconciliation и моделируемый Takeover: сначала закрывается agent writer, затем checkpoint, затем human lease. Произвольный код, shell или реальные внешние инструменты не выполняются.

## Исходники и проверки

```sh
npm run typecheck
npm run build
npm test
npm run verify
```

Первые три команды используют только приложенные файлы и Node. TypeScript 5.8.3 включён как build-time tool; React 16.0.0 / ReactDOM 16.0.1 включены локально. Это точно указанные версии данной сборки, не рекомендация для нового production-приложения. Лицензии — `licenses/`.

`npm run verify` сверяет исходный архивный состав с `CHECKSUMS.sha256`. После изменения исходников или повторного прогона отчётов несовпадение ожидаемо. `npm test` создаёт изолированные временные данные и не изменяет вашу `data/`.

Браузерные тесты — дополнительный, не runtime-инструмент. Нужны Python, Playwright и Chromium, не включённые в архив:

```sh
# Отдельно запустите npm start в пустой тестовой data-directory.
TEST_BASE_URL=http://127.0.0.1:4310 python tests/browser_e2e.py
```

На стенде сборки навигация Chromium на HTTP-origin заблокирована администратором. Поэтому выполненный браузерный прогон использовал `UI_BRIDGE=1`: настоящее приложение и видимые UI-действия, настоящий HTTP backend, но bearer bridge и polling вместо native cookie/SSE transport. **Это не проверка браузерных cookies, перезагрузки storage или native-origin reconnect.** Нативный серверный SSE и cookie flags проверены отдельными Node HTTP tests.

## Состав

`apps/web/src` — TSX-компоненты и стили; `apps/server/src` — domain, persistence, HTTP, simulator; `packages/contracts` — общие типы, каталог и schemas; `fixtures` — объявленные synthetic scenarios; `dist` — готовая автономная сборка; `tests` — исходники проверок; `reports` — raw результаты и screenshots; `docs` — исходная спецификация, API, архитектура и ограничения.

Полный перечень границ этой поставки — **`docs/LIMITATIONS.md`**. Итоговая приёмка не считается завершённой по одному зелёному unit-test или по успешному Trial.
