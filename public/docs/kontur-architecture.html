Как регулятор создаёт политику

01 / 06
КЛЮЧЕВАЯ ИДЕЯ

Сначала сегмент, затем правила для сегмента

Политика не прикрепляется вручную к каждой задаче или ноде. ИТ-ландшафт сначала классифицируется через системы и репозитории. Регулятор выбирает сегмент, публикует для него требования, а оркестратор находит их при работе с конкретным репозиторием.

01

Сегментация ИТ-ландшафта

Repository связан с System; System содержит Business Domain и Platform Type.

GIT REPOSITORY

SYSTEM
Savings Core

INHERITED SEGMENT
retail.backendАвтоматически следует из метаданных System
Другие сегменты: retail.frontendretail.datacorporate.backendcorporate.data
Сегмент нельзя подменить настройкой команды. При подключении Git-репозитория Platform Engineer видит унаследованный Segment; он не должен произвольно понижать его или менять. Команда получает права на ресурс отдельно от классификации системы.

ГЛАВНЫЙ ПРИНЦИП

Оркестратор сам находит нужные требования

Он получает задачу и её репозитории, определяет сегменты, загружает закреплённые Policy Packages и составляет Regulatory Plan. Во время исполнения подаёт в конкретный узел только применимые обязательства. После выполнения проверяет результат и формирует Evidence Report.

HG SDLC · fixed workflow

Поскольку граф известен заранее, Regulatory Plan сопоставляется с фазами: Specification, Implementation, Tests, Result. Перед каждым узлом оркестратор передаёт его часть плана.

AI Manager · agent directed

Полный граф заранее не задан. При выборе следующего Work Intent Manager сопоставляет его с условиями Regulatory Plan и подключает нужные obligations.

Оркестратор отвечает за инъекцию. Системные Before Run / After Run выполняются независимо от того, какие рабочие узлы добавила или переименовала команда.

03 / ENVIRONMENT · RUNTIME ISOLATION

Что такое Sandbox и как он создаётся

03 / 06
ДВА УРОВНЯ ИЗОЛЯЦИИ

MicroVM защищает хост. Anthropic Sandbox ограничивает процессы агента.

Кодинг-агент работает в гостевой среде с выделенным workspace. Внутри неё процессный Sandbox ограничивает файловые операции и сетевые обращения. Внешние Git, Task Tracker и Jenkins CI доступны только через настроенные Resource Bindings.

01

Из чего состоит Sandbox

Платформа задаёт физическую границу исполнения и внутренние правила для запущенного кода.

HOST INFRASTRUCTURE · ВНЕ РАБОЧЕГО ПРОЦЕССА АГЕНТА
microVM · Isolated guestизоляция от хост-машины
Anthropic Sandbox Runtime
Coding agentИсполняет шаги, команды и инструменты
Run WorkspaceCheckout ревизии, файлы, diff и тесты
File restrictions · Network restrictions · Process/tool limits
CPU · RAM · Disk · TTL · max parallel Runs
ВНЕ microVM · ПО ГРАНТАМ
Git RepositoryRead / Write / Create PR
Task TrackerProject scope
Jenkins CIJob / pipeline scope

Стрелки доступа здесь подразумевают проверяемые разрешения. Сетевое соединение само по себе не выдаёт право выполнять все операции во внешней системе.

microVM · граница хоста

Отделяет выполнение кода проекта, сборку, тесты и сторонние зависимости от хостовой ОС и других рабочих сред. Ограничивает объём выделенных вычислительных ресурсов.

Anthropic Sandbox · граница процесса

Ограничивает доступ агента и охваченных Sandbox процессов к файлам и сети внутри microVM. Не заменяет виртуализацию и требует явно заданной области действия инструментов.

02

Для чего нужны ограничения

Безопасная рабочая среда не наследует права сотрудника и не расширяет их автоматически.

Можно в разрешённом scope

  • Читать и изменять рабочую копию проекта в выделенном workspace.
  • Запускать разрешённые команды, проверки и тесты.
  • Создавать ветку и pull request при наличии Git Permission.
  • Работать с подключённым Project Task Tracker и разрешённой Jenkins job.

Не выдаётся автоматически

  • Произвольная запись на хост-машину и в другие рабочие среды.
  • Личные доступы сотрудника и production credentials.
  • Произвольный запуск CI jobs или изменение защищённой конфигурации.
  • Самостоятельное расширение агентом scope или Permissions.
Изоляция и доступы — разные уровни. MicroVM удерживает процессы внутри гостевой среды; Anthropic Sandbox ограничивает их файловые и сетевые операции; права внешних систем определяют разрешённые действия в конкретном Git, Task Tracker или Jenkins CI.

Как КОНТУР управляет знаниями

04 / 06
ЕДИНАЯ ПРОДУКТОВАЯ ИСТИНА

Граф связывает факты, документы объясняют их

У каждого продукта один Product Knowledge Graph с контролируемой публикацией. Командные знания дополняют его, а Regulatory Context хранится в отдельном контуре. Для реализации предлагается гибрид: версия документа + маленькая онтология + граф связей + retrieval с правами доступа.

01

Единая онтология и Product Knowledge Graph

Онтология задаёт типы объектов и связей; граф связывает знания с реальными системами.

ПРИМЕР · КОПИЛКА / ACTIVATION
PRODUCTКопилкаКанонические продуктовые правила
HAS_FEATURE
FEATUREActivationУсловия первого пополнения
IMPLEMENTED_BY
SYSTEM / REPOSITORYSavings Corebank/savings-api
ТИПИЗИРОВАННЫЕ СВЯЗИ · ПРЕДЛОЖЕНИЕ
Product → HAS_FEATURE → FeatureFeature → IMPLEMENTED_BY → SystemSystem → HAS_REPOSITORY → RepositoryTeam → RESPONSIBLE_FOR → FeatureDecision → GOVERNS → Feature
Предлагаемая модель. Для графа достаточно небольшой версионированной онтологии: Product, Feature, System, Repository, API, Decision, Team и связей между ними. Источником истины остаются утверждённые документы и записи с автором, версией и ссылкой на источник. Не нужно превращать каждое предложение в отдельную вершину.
02

Три слоя Context Supply Chain

Product Knowledge, Regulatory Context и Team Knowledge отделены друг от друга.

1. Product Knowledge

Общий для продукта утверждённый Knowledge Graph: бизнес-правила, функциональность, API, решения и связи. Все команды продукта читают разрешённое; публикация контролируется.

Broad read · Controlled publication

2. Regulatory Context

Требования соответствующих сегментов берутся из версионированных Policy Packages. Они принадлежат регулятору, не копируются в Team Knowledge и применяются оркестратором.

Policies · Plan · Evidence

3. Team Knowledge

Командные conventions, patterns и подтверждённые lessons learned. Они помогают команде, но не подменяют канонические продуктовые правила.

Team-scoped · Reviewed
Task, Run State, текущий diff, артефакты и состояние Flow — operational context. Runtime добавляет их автоматически, но они не являются четвёртым слоем базы знаний. Run History является Evidence, а не автоматически опубликованным Knowledge.
03

Как знания появляются и обновляются

Новые сведения проходят управляемую публикацию, а не попадают в граф из чата или Run напрямую.

Source / DiscoveryДокумент, решение, инженерное наблюдение
→
Knowledge ProposalАвтор, текст, тип сущности, связи, источник
→
ReviewПроверка владельцем и разрешений
→
Approved / PublishedВерсия и provenance закреплены
→
SupersededИзменения без потери истории
1
Предложение

Участник команды добавляет утверждение и подтверждающий документ; отмечает, к чему оно относится.

2
Проверка и конфликт

Рецензент проверяет точность, устаревшие версии и противоречия текущему Product Knowledge.

3
Публикация

Создаётся новая версия записи и при необходимости связи графа. Владелец и provenance сохраняются.

4
Использование

Assistant и Flow извлекают только разрешённые знания из одобренной версии или допустимого team scope.

Run History ≠ Knowledge. Агент может подготовить draft/Proposal по результату работы, но его вывод не становится каноническим автоматически. Права knowledge.contribute и knowledge.review отделены.
04

Как лучше устроить хранилище и поиск

Практическая рекомендация: сочетать документы, онтологию и граф, а не выбирать что-то одно.

Вариант A

Только документы + RAG

Быстро запускается, хорошо ищет текст и фрагменты. Но трудно надёжно объяснять зависимости Product → Feature → System → Repository.

Подходит: для простого справочника без сложной навигации по связям.

Вариант B

Только knowledge graph

Явные связи и impact analysis, но дорого описывать каждый факт графовой схемой. Теряется богатый контекст документов.

Подходит: для структурированного реестра систем и зависимостей.

Рекомендуется

Гибрид: RAG + Graph

Утверждённые тексты хранятся с версиями и provenance, небольшой типизированный граф задаёт связи; поиск сочетает атрибуты, граф и текст.

Плюс: ответы со ссылками на источники и объяснимыми зависимостями.

Это архитектурная рекомендация, а не обязательный пункт исходного задания. Не нужно вводить отдельную «истину» для каждой Team: общий Product Graph дополняется разрешённым Team Knowledge и ссылками на регулирующие политики.

Пример — обновление зависимости

Для BANK-1842 runtime находит связанную с репозиторием систему и соглашения команды, разрешённую ревизию знаний продукта, а также Regulatory Plan по сегменту retail.backend. Исполнитель получает только релевантные выдержки и ссылки на версии; исходные корпоративные документы целиком не инжектируются без необходимости.

Scope сохраняется при извлечении. Наличие записи в графе не означает права читать её текст. Поиск и построение контекста фильтруют источники по доступам; источники ответов должны быть прослеживаемыми.
Knowledge — управляемые данные и связи, не необработанный лог Runs.

Как работает контекстный ассистент

05 / 06
КОНТЕКСТ И ПРОИСХОЖДЕНИЕ

Один чат — два уровня понимания

КОНТУР предоставляет контекстный чат и общие Skills. Если вопрос требует понимания внутренних узлов, логов и состояния Run, чат передаёт запрос Deep Run Assistant выбранного оркестратора, а не выдумывает ответ. Все запросы и результаты ограничиваются эффективными Permissions пользователя.

Общие Skills КОНТУРа

Поиск в Knowledge, объяснение lifecycle, анализ задач по тегам, рекомендации по Flow, подготовка Knowledge Proposal. Skills имеют версии и работают в пределах контекста и прав пользователя.

Deep Run Assistant провайдера

Например, hg-sdlc-run-diagnostics@version и инструменты get_run_state, get_node_logs, read_git_diff, get_regulatory_plan, get_evidence_report.

Deep Assistant принадлежит orchestration provider. КОНТУР предоставляет единый чат, identity и контекст, но не притворяется, что знает внутреннюю структуру любого Flow. Интеграция провайдера подключается только при наличии реального соответствующего контракта.

06 / TRUSTED AUTONOMY · RELEASE · PRODUCTION

Что такое Trusted Capability

06 / 06
ГЛАВНЫЙ ОБЪЕКТ ДОВЕРИЯ

Выпускается не агент, а проверенный способ работы

Trusted Capability — релиз конкретной версии Flow или manager-конфигурации для определённого тега задач и заданных технических границ. Сначала команда работает в Supervised режиме, затем фиксирует snapshot, проверяет его в UAT и явно принимает риск. Production исполняет только опубликованный snapshot.

01

Что такое Trusted Capability

Объект доверия — конкретная способность решать определённый вид задач в ограниченном scope.

НЕ АГЕНТ И НЕ ВЕСЬ TEAM SPACE

Dependency Update · dep-update

Логическая Capability связывает Product, тег класса задач, рабочий Flow и историю качества. Доверенной автономностью обладает не «любой coding agent», а зафиксированный релиз этой Capability с точными версиями и границами.

Product: КопилкаTag: dep-updateFlow: Dependency Update v1.4Runtime: HG SDLCScope: approved repositories

Capability — развиваемая сущность

Существует в командном рабочем пространстве, имеет конфигурацию, историю запусков, статистику, версии и ссылку на опубликованные релизы.

Trusted Capability Release — неизменяемый пакет

Фиксирует проверенный способ исполнения. Production использует именно Release Snapshot, а не текущий Draft и не произвольно выбранные новые Skills.

Тег сам по себе не даёт автономности. Одинаковый тег может встречаться на разных Task Boards продукта; маршрутизация возможна только если существует активный доверенный релиз и задача находится в разрешённом scope.

Неизменяемость — принцип доверия. Каждый production Run получает версии из выпущенного snapshot. Замена модели, Requirement, Skill или runtime не происходит незаметно; для значимого изменения нужен новый кандидат на выпуск.
04

Путь к автономному выпуску: UAT и принятие риска

Benchmark необязателен, а UAT исполняет ровно тот snapshot, который затем попадёт в production.

UAT без Human Gates

Автоматически эмулируются тестовые сценарии и тестовая корзина, если она существует. Проверки фиксируются для той же версии Release Snapshot. Не тестируется один пакет с последующим выпуском другого.

Явное принятие риска

Принимающий субъект видит UAT, историю, Regulatory Evidence, scope, необязательный Benchmark и ставит явную отметку с комментарием. Нет корзины — «тестовой корзины нет». Менее 100 завершённых прогонов — высокий риск из-за малой статистики.

Benchmark optional. Успешный Benchmark не выпускает capability автоматически. Требуются freeze, UAT и явная фаза Risk Acceptance; в текущей демонстрации они моделируются, а не выполняются на реальных внешних системах.

Роутинг задач

Задачи с тегом dep-update могут приходить из разных Task Boards одного продукта. Это не расширяет видимость: люди видят только свои командные доски и Runs, а исполняемый scope релиза остаётся неизменным.

Мониторинг и реакция на исключения

Платформа отслеживает accepted/failed, latency, cost, token use, Policy Verification и здоровье зависимостей. Ошибки, отзыв политик и нарушения границ приводят к оповещениям, остановке новых Runs или приостановке capability.

«Эмулировать продакшн» — действие демонстрационной версии. Оно показывает автономное прохождение подходящих задач без Input/Approval, но не означает фактического исполнения инженерных изменений в Git и CI.
06

Версии, миграция политик и отзыв доверия

Один релиз не переписывается. Для изменившегося поведения создаётся новая версия capability.

EXAMPLE · POLICY UPDATE

Release v1.5Новая оценка · UAT · риск

Изменился Policy Package

КОНТУР находит затронутые репозитории, команды и релизы по dependency graph.

2
Создаётся новая версия

Копируется выпущенная конфигурация; Policy @7 → @8 без изменения предыдущего snapshot.

3
Переоценка

Применимые тесты, optional Benchmark, UAT того же snapshot и Risk Decision.

4
Замена или приостановка

После нового релиза прежний становится Superseded. При Withdrawn/Revoked приём новых автономных задач может блокироваться.

Хорошая статистика старой версии не доказывает новую. Она остаётся контекстом для решения, но изменение политики, модели или runtime должно быть проверено отдельно. Новое поведение никогда не подменяет опубликованный snapshot.
Автономность ограничена тегом, Product, Permissions и immutable Release Snapshot.
